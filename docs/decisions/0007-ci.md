# 0007: CI checks that the checker can still see failures, not just that RelayGuard reports none

Status: Accepted (Phase 8, steps 8a and 8b, commits 0ca60ff, b20348a and 446218e, the CheckState DB test)
Date: 2026-11-20 (plan approved by the user 2026-11-19, all defaults Q1-Q10, docs/phase8-plan.md:144-149)

## Context
The roadmap's acceptance for Phase 8 is "CI fails if the harness reports any violation" (docs/ROADMAP.md:58).
That is necessary but not sufficient: a CI job can stay green because nothing was checked. Three ways that
happens here, each one real for this codebase:
1. The DB tests skip themselves unless `RELAYGUARD_DB_TESTS=1` is set (internal/dbtest/dbtest.go:73-75). Before
   8a, the existing workflow was green and, with no `RELAYGUARD_DB_TESTS` and no database, every `TestDB*` skipped
   (inferred from the workflow and dbtest.go:73-75; that run used no `-v`, so its log shows no skip lines;
   docs/phase8-results.md section 1, run 44654164320).
2. `chaos` exits 1 both for "violations found" and for `log.Fatal` (bad flag, missing secret, DB down), so an exit
   code alone cannot tell "the naive receiver failed as expected" from "nothing ran"
   (scripts/ci-chaos-gate.sh:5-8).
3. A checker that always reports 0 violations keeps every RelayGuard run green (docs/phase8-plan.md:78-80).

## Options considered
1. **Gate on the chaos exit code.** Simplest. Rejected for reason 2 above.
2. **A `-expect` flag in cmd/chaos.** Rejected in the plan: it would change the exit-code meaning that earlier
   results docs rely on (docs/phase8-plan.md:76).
3. **A gate script on the RESULT line (chosen).** `scripts/ci-chaos-gate.sh` requires the expected exit code AND
   exactly one `RESULT target=<t>` line with the expected `seeds=`, then `failing_seeds=0 violations=0` (clean) or
   `violations >= 1` (naive control). It has its own self-test on SYNTHETIC canned logs, run as the chaos job's
   first step (scripts/ci-chaos-gate-test.sh).
4. **Retry flaky chaos runs.** Rejected: a red run is investigated and recorded, not re-run until green; the gate
   reads only `seeds`, `failing_seeds`, `violations` and the exit code, never restarts, kills or the done/stale
   split, which vary run to run (docs/phase8-plan.md:82-84).
5. **Run CI on Windows like local development.** Rejected (Q1): service containers run only on Linux runners, so
   CI is `ubuntu-24.04` with plain bash (docs/phase8-plan.md:33-36). Consequence below.

## Decision
- Two parallel jobs, each with its own Postgres 17 service: `test` (secret scan, gofmt, vet, migrations, all Go
  tests with DB tests on, then a skip guard that fails if the dbtest skip message appears or no `--- PASS: TestDB`
  line does) and `chaos` (crash seeds 1-3 and poison seed 1 against RelayGuard must be clean; naive seeds 1-3 must
  report violations) (docs/phase8-plan.md:38-69).
- The naive run is a **negative control**: it checks on every push that the checker still detects the failures it
  exists to find. cmd/naive is unchanged (project rule 4).
- Each guard was shown to fail with a deliberate break on a throwaway `ci-red/*` branch (pushed and deleted with
  the user's OK, never merged): 8a-db and 8a-skip for the test job, 8b-app and 8b-checker for the chaos job. Run
  ids, failing steps and RESULT lines verbatim are in docs/phase8-results.md.
- Webhook secret generated per run and masked, no GitHub secrets; actions pinned to full commit SHAs;
  `permissions: contents: read` (docs/phase8-plan.md:47-49, :89-92).

## Consequences
- The red proof `ci-red/8b-checker` (`sim.CheckState` returning nothing) passed every unit and DB test; only the
  naive control turned it red. That showed CheckState had no Go test of its own. `TestDBCheckStateRules`
  (internal/sim/check_db_test.go) now covers each of its rules with a positive control. It calls the exported
  CheckState (check_db_test.go:127), so by reading the test the same break should also fail the test job; the
  446218e commit message says six checker mutations fail it locally. This was not re-run as a CI red proof
  (docs/phase8-results.md section 8).
- CI numbers are a regression signal, not evidence: GitHub-hosted hardware and wall-clock kill timing make them
  not comparable to local results, and they go in no results table (docs/phase8-plan.md:94-97). A green chaos run
  is one sample, not proof of absence.
- CI runs on Linux with Go from go.mod (1.26.0, no toolchain line) while local evidence was built on Windows with
  go1.27.4 (docs/phase8-plan.md:131-132). A Linux-only failure would be a portability finding, not noise.

  are not in CI (Q4), add only if job time allows.
